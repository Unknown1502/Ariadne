# Architecture review

Prompt 17, run as a hostile pass over the repository rather than a summary of it. The method
was to look for **claims the code does not honour** — docstrings, docs, and config options
that promise something no code path delivers.

That framing found ten. Eight were real, and five of those were of the same shape:
*a capability that is described confidently and implemented partially or not at all.* For a
project whose entire thesis is "explanations should have to prove themselves", that is the
most damaging class of defect there is.

All eight are fixed. Findings are listed with the evidence that proved them.

The pattern recurred three times before it was automated away. F1 was found by reading the
adapter list; F2 by asking "where else?" straight after; F8 by finally writing the twenty-line
script that answers the question for every setting at once. The lesson is not that these were
subtle - it is that a human check which has to be *remembered* will be forgotten, and the
third occurrence is the one that should have been a test the first time.

F9 is a different species: not a missing implementation, but two present ones that were
never checked against the systems they talk to. Verified against live SDK documentation
rather than memory, because the two adapters this project cannot run locally are exactly
where "675 tests pass" stops being evidence of correctness.

F10 is a third species, and the one that took longest to think of: an implementation that
*was* exercised on every CI run and still went unchecked, because what it produced was
console output and nothing read it. It hid a forked hash chain in the append-only ledger —
the structure this project points at when it says history cannot be rewritten.

---

## Findings

### F1 — `RUNTIME_STORE=firestore` silently used local storage · **CRITICAL** · fixed

`Settings` accepted `runtime_store="firestore"`, but `open_runtime_store()` returned
`LocalRuntimeStore` unconditionally. `FirestoreRuntimeStore` did not exist.

The damage was not the missing adapter — it was that `/api/v1/system` reported
`runtime_store: firestore` to the console while the process wrote JSON files. Ariadne would
have displayed a false cloud-proof claim, generated by the system built to catch false
claims.

**Evidence:** `grep "class .*RuntimeStore"` returned one class; the factory had no branch.

**Fix:** wrote `FirestoreRuntimeStore`; the factory now dispatches and raises rather than
falling back. Both stores run through one parametrized contract suite — 74 assertions,
each executed twice — so the two cannot drift apart. The Firestore store is tested against a
client double, which covers adapter logic and *not* real Firestore; that boundary is stated
in `tests/fakes.py` and `docs/limitations.md`.

### F2 — `EVENT_BUS=pubsub` had the identical bug · **CRITICAL** · fixed

Found by asking "where else does this pattern occur?" immediately after F1. `build_event_bus()`
existed and was correct; nothing called it. `api/main.py` constructed `LocalEventBus`
directly, so the Pub/Sub setting was ignored while `/api/v1/system` reported it.

Worth recording that F1's fix did not generalise on its own. A configuration option is only
real when something reads it, and neither the type checker nor the test suite noticed that
two of them were decorative.

**Fix:** the API builds the configured bus. `PubSubEventBus` gained the lifecycle surface
the API uses (`start`, `stop`, `snapshot`, `dead_letters`) so no caller has to branch on
transport. Its `dead_letters` returns empty with a docstring saying why — Pub/Sub owns the
dead-letter topic, and an empty list here is "not the place to look", not "nothing failed".

### F3 — Scheduled re-audits were a stub with a confident docstring · **HIGH** · fixed

```python
def run_due_audits(self, now=None):
    """Execute re-audits the Governor scheduled and whose time has come.
    This is the other half of autonomy: the worker performs it later..."""
    for audit in self._runtime.due_audits(moment):
        self._runtime.mark_audit_executed(audit.id, moment)   # ...and nothing else
```

It marked audits executed without auditing anything. The Governor's `SCHEDULE_REAUDIT`
action therefore led nowhere, and a test asserting `run_due_audits()` returned a non-empty
list passed happily against the fake.

This is precisely what the operating contract forbids: *"Do not call a rule-based script an
autonomous agent."*

**Fix:** a due audit now re-emits a `MODEL_VERSION_DEPLOYED` event for the family's current
scope and publishes it, so a scheduled re-audit takes the same path as an external trigger —
same idempotency, same checkpoints, same lineage. A separate "internal" path would have been
a second pipeline implementation that nothing else tests. The audit is marked executed only
after the event is accepted; marking first would make a publish failure look like completed
work. Three tests replace the one that passed against the stub.

### F4 — The agent audit trail was empty for the entire build · **HIGH** · fixed

`base.py` opened with **"Recorded.** Every attempt writes an AgentInvocation"** and
`check_tool` claimed **"Denials are recorded, not just raised."** Neither was true.
`AgentInvocation` and `ToolCall` objects were constructed and dropped; `append_audit()` was
defined and never called; `audit_events` had never held a row.

The `check_tool` case was the worse one — a denied privilege escalation surfaces to the
caller as an exception and nothing else, so if that method does not record it, nothing does.
The single most security-relevant event in the system was leaving no trace.

**Fix:** added an `AuditSink` abstraction with a ledger-backed implementation, wired into
every reasoning agent by `build_pipeline`. A full investigation now writes five rows;
denials write a `TOOL_CALL_DENIED` row before raising.

**The fix's own bug is worth recording.** The first version wrote nothing, because
`_appended_at()` sniffs objects for a timestamp field and knows about `created_at` /
`computed_at` / `executed_at` — while `ToolCall` has `called_at` and `AgentInvocation` has
`started_at`. A deliberate `except Exception: pass` in the sink turned that 100% failure into
something indistinguishable from success. `append_audit` now uses the timestamp it is already
passed, and the sink **logs** what it swallows. Best-effort is a reasonable policy for an
audit write; silent is not.

### F5 — Registry routing was never exercised on the live path · **MEDIUM** · fixed

`AgentRegistry.route()` enforces that a message reaches an agent only if its manifest
declares both the capability and the payload schema. It was thoroughly tested and never
called outside tests — the pipeline invoked agents directly. The architecture docs describe
routing as a control; it was a control that nothing consulted.

**Fix:** the pipeline routes through the registry before invoking the Investigator and the
Experimenter, so a quarantined or mis-declared agent now actually blocks work.

### F6 — `AgentMessage` is defined and never constructed · **LOW** · accepted, documented

The envelope type carrying capability, payload schema, and routing metadata is dead code.

Assessed and deliberately not "fixed" by forcing it into the pipeline. The *substance* of the
typed-handoff claim is real: `Claim`, `Evidence`, and `Verdict` are validated Pydantic objects
and are the only things that cross agent boundaries. Wrapping them in an envelope for the
sake of using the class would add indirection without adding a guarantee. The audit sink can
record an `AgentMessage`, so it has a use when handoffs need to be logged individually.

### F8 — Eleven more settings that nothing read · **HIGH** · fixed

Found by asking the F1/F2 question systematically instead of twice: *which declared settings
does any code actually consult?* A twenty-line script over `config.py` answered it.

Eleven of thirty-two were read by nothing. Five were functional settings silently doing
nothing:

| Setting | What an operator would reasonably expect | What happened |
|---|---|---|
| `EVIDENCE_VALIDITY_DAYS` | changes staleness, audit priority, debt | `LineageService` used a hardcoded 90 |
| `AGENT_LOOP_BUDGET` | caps agent retries | manifests hardcoded 3 / 2 / 1 |
| `AGENT_TIMEOUT_SECONDS` | caps agent time | manifests hardcoded 30 / 60 / 15 |
| `GEMINI_MAX_OUTPUT_TOKENS` | caps response size | agents used the default |
| `GEMINI_TEMPERATURE` | changes sampling | every agent pinned 0.0 |

The other six were flags for capabilities that do not exist (`ENABLE_MEMORY_BANK`,
`ENABLE_AGENT_GATEWAY`, `ENABLE_MODEL_ARMOR`, `CLOUD_STORAGE_BUCKET`), a topic name no
subscriber read (`PUBSUB_INVESTIGATION_TOPIC`), and unused metadata (`APP_ENV`).

**Fix, by category rather than one at a time:**

- **Wired**: validity window into `LineageService`; max output tokens into `GeminiClient`;
  `APP_ENV` into `/api/v1/system`.
- **Wired as ceilings, not overrides.** `AGENT_LOOP_BUDGET` and `AGENT_TIMEOUT_SECONDS` now
  tighten every manifest and never loosen one. Per-agent budgets are deliberate — the
  Verifier gets a single attempt because a deterministic computation that failed once fails
  identically — and a global override that raised them would erase that reasoning.
- **Deleted.** `GEMINI_TEMPERATURE` is gone. Every agent pins 0.0 so the same explanation
  compiles to the same claim; a knob whose only effect is to break that guarantee should not
  be offered. `PUBSUB_INVESTIGATION_TOPIC` is gone too — Terraform only ever created one
  topic.
- **Rejected loudly.** The four unbuilt-capability settings now fail startup with a message
  naming what was requested. They were already documented as unintegrated; a flag that
  accepts `true` and does nothing turns an honest gap into a quiet false claim.

**Regression test.** `tests/unit/test_config_is_honest.py` scans every declared setting and
fails if anything is read by nothing. This is the third occurrence of the pattern, so the
check is now automated rather than remembered.

### F7 — `/api/v1/stream` is unused · **LOW** · accepted, documented

The SSE endpoint works; the console polls instead, because polling makes "the page only
reads" easy to verify and needs no reconnection logic. Left in place as a working endpoint
rather than deleted or claimed as the console's mechanism.

### F9 — Two cloud adapters, written from memory, never run against the real SDK · **CRITICAL** · fixed

`GeminiClient` and `FirestoreRuntimeStore` are the two integrations this system cannot
demonstrate locally, so both were checked against live google-genai and
google-cloud-firestore documentation (via Context7) rather than trusted as written. Two real
defects turned up, both invisible to 675 passing tests because the test doubles were shaped
by the same assumptions as the code they stood in for.

**Gemini: `finish_reason` was never read.** It lives on `response.candidates[0]`, not on the
response itself, so nothing checked it. A response truncated at `max_output_tokens` arrives
as JSON cut off mid-structure — indistinguishable from malformed JSON to the parser. That
was classified retryable. Every agent runs at temperature 0, so a retry reproduces the
identical truncation, and the loop budget drains reproducing a certainty. The operator then
reads "malformed JSON" and looks for a prompt bug that isn't there. Fixed by reading
`finish_reason` and `prompt_feedback.block_reason` and raising a new `AgentResponseRejected`
(non-retryable, but *recorded* — an unaudited rejection would recreate F4 on the one path
that actually calls a real model) that names the real cause and points at the actual fix
(`GEMINI_MAX_OUTPUT_TOKENS`).

**Firestore: caught the wrong exception class.** `create()` raises
`google.api_core.exceptions.Conflict` — confirmed from Firestore's own gRPC error mapping,
`ALREADY_EXISTS -> Conflict`. The adapter caught `AlreadyExists`, a *subclass* of `Conflict`.
Catching a subclass does not catch the parent, so on the Firestore path, the second worker
racing for an idempotency key got an unhandled exception instead of the `None` meaning
"already claimed" — duplicate-event safety, this project's headline reliability guarantee,
was broken on cloud infrastructure while every local test passed. It passed because the test
double raised a bare `DocumentExists` that happened to satisfy the buggy handler, making the
fake more forgiving than the system it modelled. Both the adapter (now catches `Conflict`,
the wider and correct catch) and the double (now raises a `FakeConflict` that mirrors the
real subclass relationship) were fixed together — fixing one without the other would have
left the bug re-hideable behind a too-forgiving fake.

**What this changes about the rest of the audit.** F1–F8 were found by asking "does this
code path get exercised by anything?" F9 asks the sharper question underneath that: *for a
path that is exercised only by a hand-written double, does the double enforce the same
constraints as the real dependency?* A test suite proves code does what its doubles expect.
It does not prove the doubles are honest. That gap is now closed for both cloud adapters and
recorded as a method — `docs/limitations.md` states plainly that the doubles cover adapter
*logic*, not the real services, and both fixes shipped with tests that reproduce the actual
failure shape (a truncated `finish_reason`, a real `Conflict`/`AlreadyExists` hierarchy)
rather than the sanitized shape the original code happened to handle.

### F10 — The hash chain forked whenever two entries shared a timestamp · **CRITICAL** · fixed

Found later than the rest, by a different method: finally asserting `run_demo.py`'s output
instead of only its exit code. The script was the largest untested module in the repository —
CI ran it and checked that it returned zero, so every number it printed was unasserted.

`expire_evidence` writes one `EXPIRES` row per affected reading, all stamped with a single
`moment`, and re-read "the previous entry" as `lineage_for_family(...)[-1]`. That query orders
by `(created_at, id)`. With `created_at` tied across the batch, the tiebreak fell to `id` — a
**content-addressed hash**. "Last" therefore meant "largest hash", which is stable and
completely unrelated to insertion order, so every row after the first linked back to the same
predecessor. One distribution shift produced four entries claiming one parent, three of them
unreachable from the origin.

It failed in both directions simultaneously. `verify_chain` compared links against sort order
and reported an **untouched history as broken** — an integrity check that cries wolf is one
people stop reading, which is the worst failure mode available to a tamper-detector. And the
chain genuinely had forked, so an entire branch could be dropped and a walk would never miss
it: tamper-evidence quietly weakened in the exact structure this project points at when it
claims history cannot be rewritten.

Fixed by making both operations properties of the *links* rather than of a sort — the tail is
the entry nothing points at, and `verify_chain` walks from the origin and reports whatever it
cannot reach. Removed rows, forged links, and a missing origin all still fail loudly and have
tests.

**What this adds to the method.** F1–F8 asked "does anything exercise this path?" F9 asked
"does the double enforce what the real dependency does?" F10 asks a third: *does anything
assert what this code **prints**?* Every existing chain test spaced its audits thirty days
apart, where the timestamp tie cannot occur — so the suite was green, the types were clean,
and the demo printed `Hash chain intact: True` truthfully, because it prints that line
*before* the distribution shift. Output that no test reads is output that can drift as freely
as a docstring, and this project's most-watched artifact was exactly that.

## The aggressive questions

**Is this just counterfactual testing?** Counterfactual testing is one mechanism inside it.
What is around it: claim compilation from prose, a validity gate that separates a broken
probe from a real null result, append-only temporal lineage, an operational debt score, and
policy-driven re-audit. The demo shows one sentence receiving four different correct answers
across four model versions — no counterfactual test does that, because a test suite has no
notion of the same claim persisting through time.

**Is this just XAI monitoring?** Monitoring watches metrics. This compiles a *specific
falsifiable prediction* from an explanation and then tries to falsify it. The output is a
verdict about a claim, scoped to a version and a distribution, not a drift alert.

**Is Gemini decorative?** No, but the honest answer is narrower than "no". It does exactly
one job: deciding what testable prediction a sentence makes. The distinction between "the
primary driver" and "contributed" is the whole difference between two benchmark cases that
share identical measurements and receive opposite verdicts. Everything after compilation is
arithmetic.

The caveat, stated in `docs/limitations.md`: the benchmark runs on the offline deterministic
reasoner, so **Gemini's claim-extraction quality is unmeasured**. The architecture makes the
LLM necessary; the evaluation does not yet measure how well it does the job.

**Is this an LLM wrapper?** The verifier cannot reach a model — its manifest raises if
declared with `uses_llm=True`, and a test greps its source. Verdicts are recomputable from
stored evidence by anyone. A wrapper's output cannot be recomputed.

**Where is the agent?** A deployment event arrives with nobody watching. Ariadne reads its
own history, finds the claim most in doubt, designs a probe, runs it, verifies it, updates
lineage, rescores debt, and schedules its next check. The choice of *what to audit* comes
from memory — that is the agentic part, not the fact that something executed.

**What happens after a crash?** It resumes from checkpoint and skips completed runs, and
`runs_reused` proves it rather than asserting it. Tested.

**What happens after a duplicate event?** Nothing, twice over: an atomic idempotency claim,
plus content-addressed IDs that make a repeat resolve to the same rows.

**Why does the triage nurse need it?** She is told a reason and cannot check it. This is the
thinnest part of the product story — she gets a verdict, not a decision she can act on — and
it is a genuine gap, not a presentation problem.

## Assessment

**Strongest:** the verifier's rule ordering. Putting validity, sample size, and stability
*before* interpretation is what makes INCONCLUSIVE a real answer rather than a fallback, and
the ablation shows removing it costs 3 false contradictions.

**Weakest:** Gemini's contribution is architecturally necessary and empirically unmeasured.
The next most valuable work is a labelled set of real explanations, not another feature.

**On the review itself:** most of the real findings were "described but not implemented", and
none was caught by a passing test suite, a clean type check, or a clean lint. Tests verify the
code that exists; they say nothing about code that was only ever described. Three questions
found everything here, and they are different questions:

1. *Does anything exercise this path?* (F1–F8 — config that was read by nothing)
2. *Does the double enforce what the real dependency does?* (F9 — a fake more forgiving than
   the service it modelled)
3. *Does anything assert what this code prints?* (F10 — a 158-line script checked only for
   exit status, hiding a forked hash chain)

Each was worth asking separately, and the third only occurred to anyone after the first two
stopped finding things. That is the argument for repeating this before submission rather than
declaring it done.

**Readiness:** the scientific core, the temporal system, and the fleet boundaries are solid
and tested. The cloud path is no longer unproven — it is deployed on `ariadne-12` and the
deployment itself found four bugs no emulator could have (a missing `google_sql_user`, a
Cloud Build substitution that only resolves inside step args, a missing
`roles/pubsub.subscriber` grant, and an nginx proxy loop). `/api/v1/system` reports the real
configuration, so what is and is not running stays checkable rather than assertable — and it
currently reports `provider: "stub"`, which is the honest answer about the one integration
still unproven.
